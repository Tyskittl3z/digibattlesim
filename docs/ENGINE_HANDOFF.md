# Browser-to-engine handoff, version 1

The browser is prepared to hand exact inputs to the engine. It does **not** run
battles or certify rules. The protocol deliberately supports only non-executing
`PREPARE_MATCHUP`; a future gameplay command must validate its own eligibility,
freeze and exact request bindings again. Never turn a valid request into permission
to run an unverified match.

## User flow and commands

1. Open the latest app and import both decks.
2. Inspect **Match evidence** for the current engine scope, precise blockers,
   stale diagnostic records and official/engine card metadata differences.
3. Click **Export simulation request** beside the after-report button.
4. From the repository root, validate the exported JSON:

```sh
python TOOLS/engine/request.py path/to/download.battle-request.json
```

A correct request for the loaded pair returns `request_valid: true`, `status:
BLOCKED`, `can_execute: false` and exit code **2**. Invalid/tampered requests return
exit code **1**. Swapped/unsupported/stale requests also cannot execute and contain
specific status/blocker codes. No CLI code path invokes the gameplay runner.

Supported engine seats remain **Jupitermon A / Amaterasumon-Toho B** with exactly
the quantities in `DECKS/`. Swapped seats require explicit mapping in a future
adapter; version 1 refuses to quietly remap them. Other decks retain browser
comparison and construction checks but inherit no engine diagnostic evidence.

## Contract

Envelope: `schema: digibattle-engine-request-v1`, `request_id`, `payload`.
The request ID is SHA-256 of canonical payload JSON: recursively sorted keys,
compact separators, UTF-8, no trailing newline. Printed card codes use ascending
ASCII ordering in compositions and identities, independent of browser locale.
Each seat includes exact raw text and its SHA-256, canonical composition/hash,
entries, filename, input kind and any original file hash. BOM and CRLF are retained.

Payload fields are exact: `protocol_version: 1`, `operation: PREPARE_MATCHUP`,
`execution_requested: false`, `matchup_identity`, `inputs`, `dependencies`,
`engine_snapshot_sha256`, `catalog_sha256`, `restrictions_sha256`.

Dependency fields are exact: `catalog`, `restrictions`, `app`, `engine_readiness`,
`mechanics`, `rules`, `pilots`, `roadmaps`. Version 1 requires the last four to be
`UNVERIFIED`; client-provided certification/eligibility fields are rejected.
The Python validator independently parses raw text, rechecks all input/composition/
matchup/request hashes, checks current source and app bindings, then enforces deck
scope. Hashes establish integrity and identity, not the authenticity of a judge.

`APP/engine/readiness.json` is generated by `TOOLS/engine/readiness.py` from current
engine files, the existing eligibility gate, current coverage/roadmap inputs,
verified-readable diagnostic records and pinned official catalog metadata. It is a
build-time snapshot; the validator recomputes it before accepting a request. The
static/portable app cannot know about later code changes until it is rebuilt.

## Rebuild and verify

```sh
python TOOLS/engine/readiness.py
python TOOLS/verify_project.py
python TOOLS/checksums.py --check
```

The first command updates the snapshot after source changes. The second rebuilds
legacy/PWA/portable outputs, validates source and release pins, and runs Node,
protocol, engine and real Chromium checks. GitHub Actions runs the same command
and requires rebuilt app files to match the committed bytes. Build and verification
require only the standard library and Node; browser tests additionally require
Playwright 1.62.0 and Chromium (set `CHROMIUM_EXECUTABLE` if needed).

`CURRENT_SHA256SUMS.txt` is the current tracked-file inventory. Refresh it after
staging changed files using `python TOOLS/checksums.py`. It excludes itself and
backup archives. `SHA256SUMS.txt` and `LEGACY_ARCHIVE_SHA256SUMS.txt` are historical
snapshot manifests and remain unchanged.
